10월의 결론 — 제작 속도와 완성 책임을 함께 가져가기

이번 달 조사에서 함께 보이는 흐름은 아이디어를 플레이 가능한 형태로 바꾸는 진입 장벽의 하락과 생성된 결과를 실제로 검증하는 일의 중요성이다. 이는 시장 전체를 계량한 결론이 아니라, Unity 공식 발표·새 연구·채용 사례를 함께 읽은 편집 판단이다.

  1. 작은 게임의 강점은 적은 콘텐츠 자체보다, 적은 규칙으로 반복되는 선택을 만드는 데서 찾는다.
  2. AI 도구 학습은 결과가 맞는지 재현해서 확인하는 능력과 묶어야 한다.
  3. 취업 준비는 특정 모델 이름보다 설명 가능한 프로젝트·의사결정·검증 자료에 연결한다.

첫 월간호라 이전 월간·주간과의 증감 비교는 할 수 없다. 이 호를 이후 비교의 기준점으로 삼는다.

02 · Balatro 역설계 — 익숙한 판정에 규칙 변경을 쌓는 구조

자료로 확인한 범위 Balatro는 LocalThunk가 개발하고 Playstack이 배급한 포커 기반 로그라이크 덱빌딩 게임이다. 공식 상점은 포커 조합과 Joker의 시너지, 목표 점수인 Blind, 덱·소모품·런 단위 성장을 설명한다. 상점에는 최근 평가가 “압도적으로 긍정적”으로 표시됐다. 이 평가는 확인 시점의 이용자 반응이며 판매량 자료가 아니다. [Balatro 공식 Steam 상점]

검증 방식: 공식 상점의 설명을 읽고 구조를 분석했다. 이번 조사에서 게임을 직접 플레이하거나 내부 데이터·개발 문서를 열람하지 않았다. 아래의 재미 해석은 외부 관찰에 따른 가설이다.

카드 조합 선택→점수·효과 확인→성장·조합 변경→더 높은 목표↻

재미 가설 A · 아는 행동으로 들어와 새 규칙을 배운다

포커처럼 이미 이름을 아는 판정을 출발점으로 쓰면 첫 행동을 설명하는 부담을 줄일 수 있다. 여기에 카드 효과가 더해지면 “이번에는 무엇을 우선할까?”라는 선택이 생긴다는 가설이다. 포커를 모르는 이용자에게는 같은 장점이 성립하지 않을 수 있으므로 첫 플레이에서 족보 이해 여부를 따로 관찰해야 한다.

재미 가설 B · 계산 결과가 다음 선택의 이유가 된다

점수가 크게 오르는 장면만 복제하면 시각적 쾌감은 만들어도 선택은 약할 수 있다. 플레이어가 효과의 원인을 이해하고 다음 조합에 대한 기대를 가질 때 다시 시도할 이유가 생긴다는 가설이다. 측정할 것은 화면의 숫자 크기보다 “왜 이 선택을 했는가”를 설명하는 비율이다.

재미 가설 C · 같은 카드가 상황에 따라 다른 가치를 갖는다

항상 가장 좋은 선택이 정해져 있으면 콘텐츠를 늘려도 판단은 반복된다. 지금 가진 조합과 다음 목표 때문에 평가가 뒤집히는 효과를 학생 프로젝트의 핵심 실험으로 삼을 수 있다. 이는 원작의 판매 성공 원인을 확정한 설명이 아니다.

03 · 복제 대신 검증 — 2일짜리 “룬 조합” 실험 설계

새 설계 제안 원작의 카드·그림·문구를 복사하지 않고, “같은 입력이 규칙 조합에 따라 다른 결과를 만든다”는 가설만 가져온다. 아래 수치와 이름은 원작 데이터가 아닌 이번 리포트의 실험용 제안이다.

AI에게 맡길 일과 사람이 판단할 일

AI에는 데이터 구조 초안, 점수 계산 함수, 오류 검사, 테스트 케이스 초안을 맡긴다. 사람은 효과가 실제로 다른 선택을 만드는지, 설명이 읽히는지, 실패한 이유가 납득되는지를 플레이로 판단한다. 생성형 AI를 런타임에 넣지 않고도 AI와 협업한 개발 경험을 만들 수 있다.

실험 계획

  1. 첫날: 사각형 UI와 텍스트로 선택·계산·라운드 종료까지 연결하고, 점수 순서와 중복 ID를 검사한다.
  2. 둘째 날: 3~5명에게 같은 설명으로 플레이를 부탁한다. 첫 선택까지 걸린 시간, 선택 이유, 예상 점수와 실제 결과의 차이, 재시도 의향을 기록한다.

팀이 정할 통과 기준의 예: 5명 중 4명이 1분 안에 첫 선택을 수행하고, 서로 다른 상황에서 두 종류 이상의 성장 효과를 고른다. 이는 업계 표준이 아니라 이 작은 실험을 판단하기 위한 사전 기준이다. 재미가 약하면 효과 수를 늘리기 전에 선택의 차이를 다시 설계한다.

04 · 실패 가능성을 역으로 설계하기

비슷한 규모의 실패작에 대해 매출·개발비·목표 이용자까지 확인 가능한 1차 자료는 이번 조사에서 확보하지 못했다. 특정 작품을 실패작으로 낙인찍는 대신, 위 실험이 실패하는 조건을 미리 적는다.

실패 가설관찰 신호다음 수정
항상 같은 성장 효과만 고른다플레이어와 상황이 달라도 선택이 고정됨경쟁 효과의 발동 조건·기회비용을 바꾸고 다시 시험
점수는 커지지만 이유를 모른다효과 적용 순서를 설명하지 못함계산 단계별 강조와 예상 결과 표시를 시험
시작하기 전에 설명이 길다첫 선택 전에 규칙 질문이 반복됨첫 라운드의 효과 종류를 줄여 한 규칙씩 노출
재도전 이유가 없다실패 직후 다른 전략을 말하지 못함다음 시도에서 바꿀 수 있는 선택을 명확하게 제시

비교의 한계 원작의 높은 이용자 평가만으로 작은 실험의 성공을 예측할 수 없다. 가격·출시 시점·홍보·취향·완성도도 영향을 줄 수 있다. 10월 매출 차트의 후보와 이 구조 분석을 동일한 흥행 순위 분석으로 합치지 않았다.

05 · AI 제작 파이프라인 — 코드를 넘어 데이터와 씬까지

관련 연구 9월에 공개된 Unity Insight는 Unity 코드와 직렬화된 에셋의 연결 관계를 LLM에 제공하는 인덱스 접근을 다룬다. 생성 코드만 읽어서는 프로젝트의 실제 연결을 모두 알기 어렵다는 문제의식을 확인할 수 있다. 저자의 시스템 설명을 읽은 것이며 도구를 설치하거나 성능을 재현하지 않았다. [Unity Insight: Code–Asset Index]

이번 호에서 직접 실행한 작은 사례

직접 실행 AI가 작성한 기획 데이터 검사 예제를 로컬 Node.js v24.16.0에서 실행했다. 전투 스킬의 ID, 비용, 쿨다운, 다음 상태를 검사했다. 정상 샘플 2행은 오류 0개, 의도적으로 손상시킨 샘플 3행은 예상 오류 6개를 모두 검출했다.

검사주입한 문제결과
식별자중복 ID 1개 + 빈 ID 1개2개 검출
비용음수 비용 + 소수 비용2개 검출
쿨다운음수 쿨다운1개 검출
상태 참조허용하지 않은 Flying 상태1개 검출

개발 파이프라인: 기획표 → JSON 내보내기 → 규칙 검사 → 오류 수정 → Unity에 반영. 문장으로 “이 데이터 괜찮아?”라고 묻는 대신, 허용 조건을 코드로 고정해 반복 실행하는 방식이다.

검증 한계: 인공 데이터에 대한 기능 확인이다. 실제 Unity 씬·빌드·ScriptableObject 가져오기, 수작업 대비 시간 절감률, 다른 AI 모델과의 비교는 측정하지 않았다. 예제 실행은 외부 API를 호출하지 않았으며, AI 작성 도구의 이용 요금은 별도다.

생산성 비교를 하려면 같은 오류가 들어간 서로 다른 데이터 세트 두 개를 준비하고 수작업 검수와 검사기 보조 검수를 비교한다. 작성·검수·수정 시간을 모두 기록하고 놓친 오류도 센다. 한 번의 성공만으로 “개발 시간이 몇 % 줄었다”고 주장하지 않는다.

조사 범위와 한계 이번 호는 공식 모집 캠페인 1개와 2차 플랫폼 공고 1개를 비교한 탐색 표본이다. 공식 자료·게시일·모집 중 상태를 모두 충족한 현행 개별 JD는 확보하지 못했다. 이 결과는 채용 시장에 공고가 없다는 뜻이 아니다. 데브시스터즈 공식 채용 페이지도 확인했으나 브라우저에 결과가 표시되지 않아 채용 건수 분석에서 제외했다. 기업 간 공통 우대 역량 빈도, 채용 증가율, 연봉은 계산하지 않았다.

이 표는 편집자의 학습 제안이다. 모든 기업의 필수 제출물이라는 뜻이 아니며, 이번 조사 표본으로 직무별 채용량을 비교할 수 없다. 개인의 포트폴리오·코드·경력 자료는 제공받지 않았으므로 현재 역량이나 합격 가능성을 평가하지 않는다.

07 · AI를 쓴 게임을 출시할 때 남길 기록

현재 문서 기준 Steam 콘텐츠 설문은 플레이어가 소비하는 AI 생성 콘텐츠를 다루며, 개발 중 생성한 콘텐츠와 실행 중 생성하는 콘텐츠를 구분한다. 런타임 생성은 불법 콘텐츠를 막기 위한 조치도 설명하도록 요구한다. 단순한 개발 효율 도구 사용과 실제 게임에 들어가는 콘텐츠를 같은 항목으로 뭉뚱그리지 말아야 한다. [Steam Content Survey]

작은 팀의 기록 양식 에셋 ID / 제작자·도구 / 생성·수정 방식 / 원본 출처 / 이용 조건 확인일 / 최종 게임 포함 여부 / 런타임 생성 여부를 한 표로 남긴다. AI를 썼다는 사실만으로 권리 문제가 해결되는 것은 아니다. 문서는 출시 시점에 다시 확인한다.

일반 적의 FSM·행동 트리와 생성형 NPC도 구분한다. 전자는 팀이 정한 규칙과 상태 전이를 구현하는 과제이고, 후자는 출력 품질·응답 지연·실행 비용·예외 처리를 별도로 설계해야 하는 과제다. 작은 프로젝트라면 먼저 규칙 기반 상호작용으로 경험을 검증한 뒤 생성형 기능의 필요성을 판단한다.
